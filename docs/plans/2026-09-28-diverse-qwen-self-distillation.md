# SciCode 多样化出题与 Qwen 原生 trace：实施计划（待审核）

状态：仅提出设计，等待用户审核；本分支暂不启动数据生产、训练或测评。

基线：从 9fd494f7f393ea2f665b61622dcecf37a84ee9cc 创建独立工作树和分支 scicode-diverse-self-distill-v4。原有 SciCode-v3、历史 JSONL、已训练检查点和测评结果保持原状。本方案在新分支上迭代，并把代码与计划同步到 yicloud 对应工作树。

## 一、目标和判断依据

目标是吸收 ScienceIDE 的自动化流水线思路，利用 SciCodePile 已清洗的科学代码文件作为开放式科学情境素材，持续产生结构化、多样且可核查的题，再由**基座 Qwen**生成自身原生的推理和答案。Kimi 主要承担出题、可选提示、参考解答和独立审查。训练样本保留 Qwen 自己的 reasoning_content 与 final answer 之间的连贯关系。

现有流水线已经具备数据源、批处理、审查和保留 thinking 的基础，但当前 author_prompt、ARCHETYPES、schema.validate_task、student_view 共同固定了三类题型和不少字段/数量门槛；run_pipeline 的角色模型缺省回退到同一模型；旧数据主要是 Kimi 推理链。前次训练后的测评出现长程循环、答案缺失和基础能力回退，因此新方案要先验证“题目多样性”和“原生推理链”能否带来实际改善，而不是直接扩大旧配方。

这里的“多样”指问题所要求的科学判断和证据路径确有变化，包括推导、反例、实验设计、模型辨识、近似条件、误差传播、方法选择、结果解释等；它不等同于随机改写同一种提问。题目可以有开放的表达和解题路径。结构化只用于机器流转、来源追溯和审查，不把题目内容压进固定的句式与清单。

## 二、目标流水线

SciCodePile 清洗文件／候选科学情境
  → 随机化“出题策略卡”与 Kimi 自由拟题
  → 最小结构化任务记录、可见信息校验
  → Kimi 参考解答与事后科学性审查
  → 基座 Qwen 多样化原生 rollout
  → 对困难题可选 Kimi 提示，再由 Qwen 续解或重新完整作答
  → 独立核查答案、推理与答案的一致性
  → 保留全量原始 trace；形成带审查证据的 SFT 候选
  → 小规模训练对照和科学测评，再决定扩量配方

每个阶段均保留输入快照、模型/提示词版本、随机种子、原始响应、状态和错误信息；同一 task_id 和 trace_id 可追溯到确切输入。阶段间通过 JSONL 或清单衔接，支持失败续跑与重复审计。

## 三、分阶段实施

### 0. 固定基线与兼容边界

1. 在新分支盘点现有 v3 产物结构与统计：题目类型、仓库/学科分布、单仓样本产率、题干相似度、题目被接受率、审查理由、推理长度、结束原因、最终答案率，以及当前科学测评结果。历史数据只读，用于对照。
2. 建立新的任务与 trace schema 版本，旧 schema 和旧读取路径继续可用；新产物写入独立目录。明确字段的“出题者可见／Qwen 可见／审查者可见”边界，并用同一渲染结果生成哈希，避免审查视角与真实答题视角不一致。
3. 把模型调用配置按角色拆开：Kimi 的 author、hint、reference、audit；基座 Qwen 的 solver。端点、模型名、采样参数、context/output budget 均可配置，运行清单记下实际值。实施前做端点能力探针，确认 Qwen 端返回原生 thinking 及终止状态。

### 1. 设计多样化出题器

1. 将当前三类 archetype 当作可复用策略种子之一，而不是穷尽的题目分类。引入可扩展的“出题策略卡”：科学领域与现象、素材类型、需要作出的判断、可用证据、交付形式、视角和表述风格。每轮从若干维度随机组合，也允许 Kimi 自拟新策略并记录其描述。
2. 利用 SciCodePile 文件、文档注释、接口、计算方法和同一仓库内相关片段构造科学情境。允许单文件、多文件、同领域跨文件以及抽象化情境等不同来源路径；记录来源片段和加工关系，便于后续审查其科学依据。
3. Kimi 在策略卡和素材的启发下自由拟题。作者输出至少提供机器可识别的题面、任务 ID/来源、预期交付和必要背景；可选字段承载假设、数据、实验条件或题型专属信息。JSON 解析与可见信息完整性是基础工程校验，题目如何构思由作者模型发挥。
4. 引入“每轮出题策略—产出—反馈”的轻量循环：批次报告展示覆盖范围、近似重复、求解表现和审查问题；下一轮可调整策略权重、增加新方向或探索较少出现的领域。保留种子、策略版本和抽样概率以便重现。这借鉴老师给出的训练语料迭代式提示词思想，随机性落实在任务选择与科学视角，而不只是文字扰动。
5. 丰富度报告作为观察和改进依据；初期记录题目所需证据、科学对象、推理动作、答案形态及语言风格等标签，可由 Kimi 标注并抽样核验。等试验数据出现后再确定是否需要特定配比。

预计改造点：factory/reasoning/prompts.py、author.py、schema.py、student_view.py、pipeline.py；新增策略卡生成/记录模块及对应测试。现有 SciCodePile 索引与仓库快照处理优先复用。

### 2. 建立参考解答与科学审查

1. Kimi 对“Qwen 实际看到的题面”独立产生参考答案、关键论证点及可能的其他有效路径；题面、参考答案、审查依据分开存储。题面信息缺失时反馈给出题器修订。
2. 自动核查围绕题目对应的科学内容进行：核心概念和假设是否成立，推导/实验解释是否自洽，所引用素材是否支持命题，答案是否回应交付要求。能运行的数值例子、性质测试或小实验可提供附加证据；开放题以论证及证据审查为主。
3. Kimi 独立复核参考解答，也审查题目的可解性、歧义及潜在多解。审查保留逐项依据、无法判定项和修订建议；可修订的题回到作者阶段，困难但有价值的题继续保留到探索池。单一 Kimi 审核模型即可开始，不设人工审核工序。
4. 审查发生在题目生成之后，而非在作者提示词中堆叠禁令。早期仅以格式损坏、信息缺失等基础工程问题阻断流水线；科学判断通过事后标签和证据来决定后续用途。

预计改造点：preflight.py、verify.py、scientific_audit.py、pipeline.py；审查结果独立存档，并在 trace 采集和导出时按 task_hash 关联。

### 3. 采集 Qwen 原生推理 trace

1. 以未受本批 Kimi-CoT SFT 影响的基座 Qwen 作为 solver。沿用原生 chat/completions 响应，分别存 reasoning_content、content、usage、finish_reason、原始响应引用、采样参数与完整对话。先确认训练框架对该 thinking 格式的真实消费方式。
2. 对同一题按可配置的采样策略收集若干条 Qwen trace：温度、提示呈现方式、思考预算和解题起点可变化，保留它们与题目策略之间的关系。采样轮数与预算在试验中根据产率和质量决定，避免预先把推理长度等同于质量。
3. 若 Qwen 遇到困难，Kimi 可提供分层提示，如提醒核对假设、指出一项需要验证的证据、建议新的检验路径。提示作为独立工件记录；Qwen 在该提示下自己完成后续推理和回答。保留原始尝试、提示、后续尝试的链路，便于分析提示是否带来真正的思维进展。
4. Qwen 的 final answer 由自己的 trace 导出；参考答案只用于核查和反馈。若采用修正答案的试验配方，需让 Qwen 基于反馈重新形成连贯的推理与最终答复，并单独标记为“反馈后 Qwen trace”。保留原始错误轨迹以支持后续研究，不将其自动当成正向完整 SFT 样本。

预计改造点：rollout.py、pipeline.py、batch.py、factory/author/llm.py（如需多端点适配）；新增提示回合编排。测试覆盖 Qwen thinking 字段、截断/空 final、续跑身份、原始尝试与提示链路。

### 4. 审查、标注与 SFT 导出

1. 将“最终答案的科学正确性”“推理过程是否支持该答案”“是否出现实质性进展”“输出是否完整”分别判定并保存证据。Kimi 负责语义审查，程序负责格式、一致性和可执行证据；审查不以 assert 通过与否代替科学判断。
2. 全部原始 trace 保留在归档层。训练候选层为完整正确且过程连贯的 Qwen trace，以及经反馈后由 Qwen 自己形成完整连贯回答的 trace。长而有价值的推理可入选；重复兜圈、结论与推理冲突等问题通过独立审查体现。未入选的 trace 连同失败原因用于后续诊断、提示实验和其他训练目标研究。
3. SFT 行保留任务策略、来源、模型与端点版本、采样参数、提示链路、审查版本与证据、Qwen 原生 reasoning_content、final content 及每段 loss 选择。提供训练视图和审计视图；导出时验证 task_hash、student_view_hash、trace_id 及 provenance 对齐。JSONL 写入采用可恢复、可核对的方式。
4. 为训练准备多个可比较的数据视图：原生完整 thinking、经 Qwen 自身重答的 thinking、不同训练损失权重/样本混合方案。先通过小规模对照决定使用方式，特别观察推理 token 对答案学习和原有能力的影响。最终训练样本的推理与答案来自同一条 Qwen 轨迹。

预计改造点：grade.py、scientific_audit.py、export.py、build_audited_sft.py、训练数据转换脚本和相关测试。现有审查历史可作为比较材料，新的发布路径采用自动审核。

### 5. 小规模试验、归因与扩量

1. 先做端到端 smoke：验证新题面、可见信息、参考答案、Qwen reasoning_content、Kimi 审查、JSONL 导出与训练模板读取全链路一致。重点检查样本内容本身，不仅检查文件存在。
2. 固定一组科学评测与留出题，按任务和训练 token 尽可能配平，分别比较：现有固定题型＋Kimi trace、开放题＋Kimi trace、固定题型＋Qwen trace、开放题＋Qwen trace；也比较带提示和直接解题。这样可以区分题目变化、trace 来源及提示的作用。
3. 报告覆盖度（领域、科学问题类型、素材来源、答案形态）、近似重复、单仓有效样本率、审核分歧/错误类型、最终答案率、推理长度分布、重复循环现象、SciCode 分题得分及其他科学能力测评。尤其对照基座 Qwen 与旧 SFT 检查是否改善“过度思考而答不出”的问题。
4. 依据 pilot 结果调整出题策略、提示方式、审查方式和训练混合，再进入更大的批次。扩量沿用现有 queue/lease/manifest 体系；Kimi 与 Qwen 的服务容量分别探测和控制，分片写入、确定性合并、幂等恢复，避免高并发重跑造成竞态和重复样本。

预计改造点：batch.py、queue.py、批处理启动脚本、报告脚本及测试。大规模吞吐量和目标样本数在 pilot 证据充分后配置，原有 10k 目标可作为后续规模目标。

## 四、验收与交付

实施完成时交付：

1. 可复现的新版本流水线和角色化配置；同一输入能追踪到题、参考解答、Qwen 原生 trace、提示链、审查和 SFT 行。
2. 一份开放式、多方向的题目样本册，展示不同科学任务如何由 SciCodePile 素材生成，以及对应的科学审查依据。
3. 一份可直接被现有 Qwen 训练模板消费的 JSONL 样本和格式验证报告，确认 reasoning_content 与 final answer 均得到正确处理。
4. pilot 对照报告：质量、覆盖、有效样本率、训练后的答题完整性与科学测评表现；根据证据提出下一轮配方。

本计划提交审核后，再按阶段改造、测试和运行 smoke。当前分支创建及计划文档本身不改变旧数据或模型服务状态。
